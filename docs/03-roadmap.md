# 03 · 개발 로드맵

**전제: 1인 개발, 아트는 AI 생성, 모바일 F2P + Steam 프리미엄.**

기간은 **전업 집중 기준**입니다. 각 마일스톤은 **"무엇이 되면 끝인가"** 를 명확히 정의해서,
다음 단계로 넘어갈지 스스로 판단할 수 있게 했습니다.

혼자 하는 개발에서 가장 위험한 건 일정이 아니라 **"이게 재미있는지 모르는 채로 3개월을 쓰는 것"** 입니다.
그래서 M1(수직 슬라이스)에 재미 판정을 몰아넣었고, 그 이전 단계는 최소한으로 줄였습니다.

| `tests/test_redraw_token.gd` | 토큰 소모, **슬롯 잠금(토큰 1회 → 광고만)**, "폐기 카드 재출현 금지" 검증 |

**완료 조건**
- 족보 판정 테스트 100% 통과
- ✅ **7장→5장→토큰 리드로우 룰의 실제 족보 분포가 숫자로 나왔다** (한국식 13족보 기준)
- ✅ **토큰 3개가 적정하다고 확인됨** — 탑이 8.85~13.23%로 목표 구간(5~12%) 안팎
- ⚠️ **로열 확률 문제 발견** — 32,000회 중 0회. 아티팩트 빌드로 끌어올릴 수 있는지 M1에서 재측정

> 이 단계를 건너뛰면 안 됩니다. GDD 2.3의 확률은 전부 추정치이고,
> 타워 스탯·비용 곡선·몬스터 HP·토큰 개수가 전부 이 분포 위에 얹힙니다.
> 여기가 틀리면 M2 이후 밸런싱을 통째로 다시 해야 합니다.

## M1 · 수직 슬라이스 (약 2주)

**목표: "재미있는가?"를 판정할 수 있는 최소 플레이어블.**

| 산출물 | 설명 |
|---|---|
| Board / Tile / 고정 경로 | 15×20 그리드, 경로 렌더, 슬롯 탭 |
| 건설 플로우 전체 | 비용 지불(첫 타워 무료) → 7장 딜 → 5장 선택 → 토큰 리드로우(슬롯 잠금) → 타워 생성 |
| BuildSheet UI | 2행 4열 손패, **실시간 족보 미리보기**, 카드별 🔄 버튼, 토큰 잔량 표시 |
| 타워 3종만 | 탑 / 원 페어 / 투 페어 (단일 대상, 무늬 특성 없음) |
| 몬스터 1종, 웨이브 5라운드 | |
| 라운드 컨트롤러 | 준비 → 진행 → 종료, 골드 보상 |

**완료 조건**
- 5라운드짜리 스테이지를 처음부터 끝까지 플레이할 수 있다
- **본인이 플레이해보고 "카드 뽑는 게 재밌다"고 느껴진다**

> **여기가 최대 의사결정 지점입니다.** 재미없으면 룰을 바꿔야 합니다.
> (토큰 개수, 딜 매수, 비용 곡선 등) 아트나 콘텐츠에 투자하기 전에 판단하세요.
> **플레이스홀더 도형으로 만드세요.** 여기서 아트에 시간을 쓰면 안 됩니다 —
> 룰이 바뀌면 그 아트는 버려집니다.

## M-Art · 아트 트랙 (M2부터 상시 병행)

혼자 하는 개발에서 아트는 **별도 마일스톤이 아니라 상시 백그라운드 작업**입니다.
코딩이 막힐 때 아트로 전환하는 식으로 굴리는 게 현실적입니다.

| 시점 | 작업 |
|---|---|
| M2 시작 전 | **스타일 시트 확정** (대표 2~3장). [assets/_prompts/00-style-sheet.md](../assets/_prompts/00-style-sheet.md) 7절 프롬프트 사용. 이게 늦어지면 뒤의 모든 에셋을 다시 만들어야 합니다 |
| M2 | 타워 10종 생성 ([프롬프트](../assets/_prompts/01-towers.md)) → 타일 크기로 축소해 구분되는지 검증 |
| M2 | **발광부 틴트 셰이더** 구축 (10장 → 40조합). 생성물의 발광부가 흰빛인지 먼저 확인 |
| M3 | 몬스터 7종 + 보스 3종 (같은 발광부 틴트 방식) |
| M4 | UI 프레임, 아이콘 (아티팩트·장비·캐릭터) |
| M5 | 스테이지 배경 10~12종 |
| M6 | 이펙트, 폴리시, 스토어 프로모션 아트 |

**철칙 3가지**
1. **M1까지는 플레이스홀더 도형만 씁니다.** 룰이 확정되기 전의 아트는 버려질 아트입니다.
2. **생성 → 축소 검증 → 채택** 순서를 지킵니다. 1024px에서 멋있어 보여도
   타일 크기로 줄이면 뭉개지는 경우가 대부분입니다. 축소 검증을 통과한 것만 채택하세요.
3. **프롬프트와 시드를 `assets/_prompts/`에 저장합니다.** 6개월 뒤에 수정할 일이 반드시 생깁니다.

상세 파이프라인은 [02-tech-architecture.md 9절](02-tech-architecture.md)을 참조하세요.

|---|---|

| **Steam** | 파트너 등록, 스토어 페이지(출시 2주 전 공개 권장), 가로 레이아웃/키보드·패드 입력, Steam Deck 검증, 빌드 업로드 |
| **AI 콘텐츠 공시** | Steam은 AI 생성 콘텐츠 신고가 **의무**입니다. 누락 시 심사 지연/거부 |

> 원래 2주에서 **3주로 늘렸습니다.** Godot의 IAP 플러그인 생태계는 Unity만큼 성숙하지 않아
> 여기서 예상보다 오래 걸리는 경우가 흔합니다. 최소 1주는 IAP에만 배정하세요.

**추천 출시 순서: Android 내부테스트 → Steam 데모/얼리액세스 → iOS**
안드로이드가 반복 배포가 가장 빠르고, Steam은 위시리스트를 미리 쌓을 수 있으며,
iOS는 심사가 가장 까다로워 마지막에 두는 게 리스크가 낮습니다.

### 현실적인 기간 ⚠️

위 표는 **전업으로 집중했을 때**의 숫자입니다. 실제로는:

| 투입 방식 | 예상 기간 |
|---|---|
| 전업 (주 40시간+) | **5~6개월** |
| 반전업 (주 25시간) | 8~10개월 |
| 퇴근 후 + 주말 (주 12~15시간) | **12~18개월** |

전업 기준에도 4.5주가 아니라 5~6개월을 적은 이유는, 1인 개발에서는 표에 안 잡히는 시간이
반드시 발생하기 때문입니다 — 스토어 계정 개설과 심사 서류, 세금·사업자 처리,
플러그인이 안 붙어서 이틀 날리기, 그리고 **M1 이후 재미가 부족해 룰을 다시 만드는 루프**.
마지막 것은 실패가 아니라 정상적인 과정입니다.

**이 일정의 전제**
- 아트는 AI 생성 + 후처리. 직접 그리면 +2~4개월.
- BGM은 라이선스 구매. 직접 작곡하면 +1개월.
- M1 이후 룰 재설계 루프가 1회 발생한다고 가정 (M1에 이미 반영).
